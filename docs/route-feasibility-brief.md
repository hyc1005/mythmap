# 专题路线可行性评估简报

更新：2026-11-09。供其他 agent 独立评估“专题巡山录”是否值得继续做、以及怎么做。

## 1. 这份简报要解决什么

项目已有两条“专题路线”，但维护者仍然迟疑：**路线目前只是按标签筛出的条目序列，和异兽谱的功效/征兆筛选没有本质区别**。需要评估：

1. 路线是否值得保留并扩展；
2. 如果值得，哪种形态能在不增加运行时依赖的前提下，提供筛选给不了的价值；
3. 实现成本、编辑成本与风险分别是什么。

请只做评估与方案，不改代码。

## 2. 项目背景（评估所需的最小上下文）

- 静态双语站点，部署在 GitHub Pages；没有运行时数据库，数据在构建期生成，随 Git 评审。
- 384 条条目：312 异兽 + 72 神灵；阅读段只覆盖五部山经（480 段），海经/大荒经仅少量交叉引用。
- 现有深度功能：同名异载/异说校读、effect/omen 标签筛选、相关条目排序、专题路线。
- 路线入口：顶部导航「专题巡山录」，区块 `#routes` 位于异兽谱之后、读图与依据之前。
- 路线点位只打开条目详情抽屉；**不启动导览播放，不占用“开始游历”状态**。这是硬约束，避免与既有播放状态机冲突。
- 详情抽屉已经改为阅读优先：插画 → 篇名 → 原文 → 白话；校读与依据、来源与说明默认折叠。

## 3. 当前实现（事实）

数据文件：`frontend/src/guide-routes.json`

```json
{
  "routes": [
    {
      "id": "omens",
      "title": { "zh": "见则志", "en": "Omens and signs" },
      "intro": { "zh": "…", "en": "…" },
      "stops": [
        { "entryId": "beast-bifang", "label": { "zh": "毕方 · 讹火", "en": "Bifang · fire" } }
      ]
    }
  ]
}
```

- 两条路线：见则志 6 站（毕方、浑夕肥遗、长右、朱厌、蜚、当康）；服佩辟邪 4 站（九尾狐、猼訑、青耕、英山肥遗）。
- 每个点位只有 `entryId` + 双语短标签；没有“为什么是这一站”“与上一站的关系”“路线结论”。
- UI：`frontend/src/components/GuideRoutes.jsx`，路线标签页 + 简介 + 点位按钮；按钮只调用 `onOpen(entryId)`。
- 验证：`frontend/scripts/verify-bestiary.mjs` 断言点位存在、双语、唯一，并确认点开条目后 `data-timeline-playing=false`。

## 4. 可用数据（决定哪些方案可行）

| 数据 | 位置 | 对路线的价值 |
| --- | --- | --- |
| `entryId` / 名称 / 原文 / 郭注 / 篇目 | `frontend/public/data/myth-world.json` | 任何路线的基础 |
| `group_key`（同名组） | `frontend/src/bestiary-metadata.json` | 同名异载、对照路线 |
| `book_key` / `form_group` / `feature_tags` | 同上 | 篇目、形貌路线 |
| `basis`（text / comparison / commentary） | 同上 | 区分正文、异说、郭注 |
| effect / omen 标签 + 出处 | `frontend/src/bestiary-semantic-tags.json` | 现有两条路线 |
| `context_place_id` / `related_entry_ids` | `myth-world.json` | 空间路线、关联路线 |
| 知名度权重 | `frontend/src/bestiary-notability.json` | 排序与降权 |
| 插画与审核状态 | `myth-world.json` / `bestiary-metadata.json` | 路线点位配图 |

限制：`context_place_id` 是文本地点锚点，不是精确坐标；不能用路线暗示真实地理距离或“事件发生地”。

## 5. 候选形态（请逐项评估）

### A. 论点式（升级现有两条，最低风险）

- 每条路线增加一句主张（`thesis`），每站增加“为何在此”（`why`）与到下一站的承接（`transition`），末尾增加收束（`closing`）。
- 读者体验：先读论点，再按顺序读 6 站，每站知道“为什么现在读它”。
- 数据/UI：只扩 `guide-routes.json` 字段与 `GuideRoutes.jsx` 渲染，不新增状态。
- 编辑成本：每站 40–80 字，一条 6 站约 400–600 字；两条约 1 天。
- 与筛选的区别：筛选给集合，路线给论证与顺序；把站点打乱，论点就不成立。
- 风险：容易写成“标签同义反复”；需要真正的编辑判断。

示例（毕方一站）：

> 毕方 · 讹火：火兆被写成“其邑”，范围只到城邑。下一站长右把“大水”放大到郡县，灾异的尺度开始变化。

### B. 对照式（最适合现有数据）

- 每站不是单条，而是一对或一组：同 `group_key`、同段比较记述、或同标签不同形貌。
- 示例：英山肥遗（鸟，食之已疠）vs 浑夕肥遗（蛇，见则大旱）；穷奇（西山经，牛形）vs 穷奇（海内北经，虎形有翼）；帝之二女的三层身份。
- 数据/UI：`stops` 需支持 `entryIds: []`；UI 可复用详情抽屉的并列/异说视图，或做双栏导读。
- 编辑成本：3–4 组即可成一条路线；比 A 少写，但每次要写“同与不同”。
- 与筛选的区别：筛选不能并排解释差异；对照本身就是阅读方法。
- 风险：UI 改动大于 A；要避免把比较记述误当同名。

### C. 空间式（同一山/水/地点）

- 沿一个 `context_place_id` 读：正文、郭注、异说、怪神、物产。
- 示例：洞庭之山（帝之二女正文 + 尧女说 + 舜妃说 + 湘君湘夫人 + 怪神）。
- 数据/UI：点位需要地点锚点与条目顺序；可加“在地图中查看”，但必须标注“文本锚点，不表示真实位置”。
- 编辑成本：1 个地点 4–6 条；需要核对段界。
- 与筛选的区别：筛选按条目属性，空间路线按“同一段文本的阅读次序”。
- 风险：容易与“此地所见”重复；必须给出阅读顺序与理由。

### D. 祭礼序列（非标签路线）

- 五山祭礼总括：山神形貌 → 祭品 → 玉 → 糈，按篇目顺序。
- 数据/UI：从 `world.text_entities` / `rite` 类条目取；不依赖 effect/omen。
- 编辑成本：中；需要核对祭礼文本。
- 与筛选的区别：完全不来自标签，能直接证明路线不是筛选换皮。
- 风险：祭礼条目较少，可能不足 6 站；需要确认覆盖。

### E. 问题链（读者视角）

- 每站回答上一站留下的问题：“什么算凶兆？”→“兆的范围有多大？”→“吉兆与凶兆能并列吗？”
- 本质是 A 的写法变体，但编辑框架更清楚；适合手机端短文阅读。
- 风险：问题链容易变成作者自问自答，需要原文支撑。

### F. 分支路线（暂不建议）

- 读者在开头选“灾异/吉兆”走不同序列。
- 需要新的状态机、返回与深链；与“不占用开始游历状态”的约束冲突风险高。
- 除非评估认为收益显著，否则不建议首版做。

## 6. 评估时请回答的问题

1. **价值**：每种形态是否提供了筛选给不了的东西？请用一句话说明“读者读完能得到什么”。
2. **数据充足性**：按现有字段，每种形态能凑出几条路线、每站几条？缺什么字段？
3. **实现**：UI 改动范围、是否新增状态、是否影响阅读位置/焦点/深链；最小组件改动是什么？
4. **编辑成本**：每条路线需要多少字、多少次原文核对；谁来做？
5. **风险**：是否暗示年代/真实地理/因果；是否把郭注或比较记述误当正文；双语是否对等。
6. **验证**：需要哪些断言（点位存在、顺序、双语、不启动导览、移动端不溢出）。
7. **取舍**：如果只能做一条，选哪个形态？为什么？

## 7. 约束与非目标

- 不新增运行时数据库或后端；不引入新依赖。
- 不改变“开始游历”的状态机；路线不自动播放。
- 不改写原文；不把比较记述、郭注混入正文。
- 不给路线编造年代、真实坐标或因果关系。
- 不追求路线数量；先证明一条路线比筛选多提供了什么。

## 8. 建议的评估方法

1. 先选 A（见则志升级）与 B（同名对照）各写 2 个站点的样张，比较“读起来是否像文章”。
2. 用同一批条目做一次筛选截图，和路线样张并排；如果读者说不出差别，方案不成立。
3. 评估 D（祭礼）是否能凑够 4 站；如果能，作为“非标签路线”的对照。
4. 给出一个最小实现顺序：数据字段 → 渲染 → 双语 → 验证；不要先做分支或自动播放。
